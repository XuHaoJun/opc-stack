# Upgrade migration completeness — design

**Date**: 2026-08-25
**Branch**: `fix/upgrade-migration-gaps`
**Goal**: running the `upgrade-opc-stack` skill handles *everything* an upstream
tag bump requires. No step survives only as prose that an operator or an agent
has to remember.

---

## 1. The problem, stated precisely

`scripts/upgrade.sh <proj> <tag>` does: fetch → verify tag → checkout →
`prepare.sh` → `docker compose build` → `docker compose up -d`. Volumes are
preserved. Therefore **every schema/format migration must either run
automatically on boot, or be run by somebody** — and today nothing in the repo
checks which of those two happened.

The 2026-08-17 Hermes incident is the reference failure: a pin bump
(`3ff0fa9`, 4 files / 4 insertions) silently ran the config ladder 34→37 on a
live volume and dropped `agent.system_prompt`. The front door ran with **no
system prompt for ≥27 hours**; it was found by a human noticing the agent had
built a prototype itself instead of filing a ticket, not by any gate.

A four-component investigation (2026-08-25) established where the same class of
failure is still live. The general shape is:

> Upstream ships migration X, triggered by Y. Does our deployment reach Y, and
> does X rewrite a key we claim to own?

### Findings

| Component | Migration mechanism | Reaches trigger? | Verdict |
|---|---|---|---|
| buzz | sqlx, **compile-time embedded** into the binary (`crates/buzz-db/src/migration.rs:15`); `BUZZ_AUTO_MIGRATE: "true"` hard-coded in `docker-compose.yml:219` | yes; failure is loud (process exits → crash loop) | **no gap** |
| paperclip | Drizzle; `server/src/index.ts:164` `if (!stdin.isTTY \|\| !stdout.isTTY) return true` auto-applies on non-TTY containers; stale schema throws `Refusing to start against a stale schema` | yes; already observed applying `0184`→`0211` on a live cluster | **no gap** |
| hermes | three layers: config ladder (boot, s6 `docker/stage2-hook.sh:552-561`), `state.db` (in-process), `hermes update` (refuses under docker) | gateway/dashboard yes; **frontdoor no** (pip install, no s6) — its config is migrated by the *dashboard* container, which mounts the same volume | latent |
| tencentdb | online `ALTER TABLE` / FTS rebuild, no version stamp (`PRAGMA user_version = 0` on all three sqlite files); failure sets `this.degraded = true` and becomes a silent no-op (`sqlite.ts:518-527`) | yes | **3 gaps** |

### The gaps this design closes

1. **`v3-meta-schemas.ts` whole-file overlay** (tencentdb). The real OPC delta
   is 3 hunks (a doc comment plus `team_id?` / `agent_id?`), shipped as a frozen
   448-line copy that `MemoryCore/Dockerfile:105` COPYs over upstream
   unconditionally. Verified against the real `v2.0.1` tag: that file changed
   (`+18 −2`), adding `userCreateWithKeySchema` and `fixedAssetListWithDetailSchema.asset_types`.
   The router namespace-imports it and `bind()` derefs lazily
   (`v3-meta-router.ts:33,92`), so after the upgrade the gateway boots,
   `/health` is green, `connectivity.sh` is green, and only
   `/v3/meta/user/create-with-key` 500s when called — while `asset_types`
   filtering is silently stripped by zod. `prepare.sh`'s `check_identical`
   does not cover this file.

2. **Bootstrap one-shots never re-run on upgrade.** A compose one-shot that
   already exists and exited 0 is not re-run by `docker compose up -d`. Only the
   hermes branch of `upgrade.sh` passes `--force-recreate`. So *buzz* and
   *tencentdb*, which do list their bootstrap in `SERVICES`, still do not
   reconcile on upgrade — and `SERVICES[paperclip]` omits `paperclip-bootstrap`
   entirely. Effect: skills, agent `adapterConfig`, and meta-registry
   registration stay at whatever the previous version wrote.

3. **`_config_version` seeded literal is stale.** Five sites
   (`patches/hermes/hermes-entrypoint.sh:126,181,400`,
   `patches/buzz/frontdoor-entrypoint.sh:184,251`) stamp `34`, while the pinned
   `v2026.8.19` default is `38` (`hermes_cli/config_defaults.py:3630`). Every
   clean install therefore runs `_migrate_to_35..38` unattended on our own
   template. Today those four steps are benign — 35/36/37 only touch values
   pinned at exactly the old default, and `_migrate_to_38` removes only
   `LEGACY_RELAY_PLUGIN_KEYS = {"nemo_relay", "observability/nemo_relay"}`
   (`relay_plugin_cutover.py:11-16`), not our `memory_tencentdb`. The hazard is
   structural: the gap widens with every hermes bump, and nothing reports it.

4. **Proxy `config.yaml` is seed-once.** `proxy-entrypoint.sh:8`
   `if [ ! -f "$CONF" ]` — after an upgrade the proxy keeps consuming the config
   generated by the *previous* version; keys added by the new version never
   appear. This is the same "seed once is not enough" lesson already learned for
   `system_prompt` and `SOUL.md`.

5. **No post-upgrade assertion that migrations advanced.** `upgrade.sh` ends by
   *printing* `verify: tests/connectivity.sh`. Nothing checks a migration
   counter, a config version, or tencentdb's degraded flag. `connectivity.sh` is
   green in every one of the silent-failure scenarios above.

6. **Risk assessment is prose.** The skill's checklist tells the operator to run
   a list of `git diff` probes by hand. That is exactly the kind of step that
   gets skipped — and it is the step that would have caught gap 1.

7. **Rollback behaves differently per component and this is undocumented.**
   buzz hard-fails (sqlx `Migrator.ignore_missing = false` → `VersionMissing`);
   paperclip *silently* runs old code against the new schema (Drizzle has no
   down migrations, and pending is computed as `available − applied`, so a
   downgrade reports `upToDate`); tencentdb has no version stamp at all, so a
   downgrade is undetectable. Restoring the volume backup is the only real
   rollback for all three.

## 2. Architecture

Four layers, each with one job. The rule that shapes the split: **anything a
machine can check must fail loudly in the machine; only genuine judgement calls
reach the operator, and they reach them as a gate, not as prose.**

```
scripts/upgrade-preflight.sh <proj> <tag>     read-only. every mechanical probe.
   │                                          exit 0 clean / 1 needs a decision / 2 blocked
   ▼
skill GATE A (human approves the risk report)
   │
   ▼
backup-volumes.sh                             unchanged; stops services, tars stateful volumes
   │
   ▼
scripts/upgrade.sh <proj> <tag>               engine. checkout → prepare → build → up
   │  ├─ prepare.sh guards       ── overlay base drift, _config_version drift → build stops
   │  ├─ Dockerfile patch apply  ── upstream context drift → build stops
   │  ├─ --force-recreate incl. the component's bootstrap one-shots
   │  └─ runs tests/migrations.sh itself (not "prints a reminder")
   ▼
tests/migrations.sh <proj>                    post-upgrade assertion gate
   │
   ▼
skill GATE B (rollback offered on failure, never automatic)
```

### 2.1 `scripts/upgrade-preflight.sh` (new)

Read-only. Replaces the hand-run probe list in `references/risk-checklist.md`
§3-§7. Emits a structured report the skill pastes into its risk report.

Shared probes (all components):

- tag exists on origin (`ls-remote --tags`)
- delta classification from the component's tag scheme
- commit-subject and diff-content risk grep (`migrat|break|schema|config|deprecat|env|api`,
  `ALTER TABLE|CREATE TABLE`) — a hint, never a gate (tencentdb subjects are Chinese)
- CHANGELOG / `releases/<tag>.md` presence and Upgrade-Guide extraction
- patched-Dockerfile build inputs still exist at the new tag, and which changed
- migration-file delta count

Per-component probes:

| Component | Probe |
|---|---|
| buzz | `git diff <old>..<tag> -- migrations/` must be **additions only** (a changed existing file means a checksum break → `VersionMismatch` hard-fail); flag any new `-- no-transaction` migration (raises dirty-state risk) |
| paperclip | count new files under `packages/db/src/migrations/`; extract the release note's Upgrade Guide; flag destructive `DROP TABLE` migrations (they make downgrade unsafe) |
| hermes | upstream `_config_version` default vs our seeded literal, and the list of `_migrate_to_N` between them; re-read `container_boot._read_container_argv` / `_is_dashboard_container` (the two private functions `tests/scientist.sh` imports and `hermes-entrypoint.sh` mirrors) |
| tencentdb | overlay base drift (`v3-meta-schemas.ts`); `deploy/panel-knowledge-combined/` still present; `MemoryProxy/src/db/binding-repo.ts` + `storage/key-utils.ts` diff (session-binding key format); `TDAI_*` env surface diff |

Exit codes: `0` nothing needs a decision · `1` findings需要人工判斷 · `2` cannot
report (tag missing, submodule absent).

### 2.2 Build-time guards

**`prepare.sh`** gains two guards, in the existing `check_identical` idiom
(fail → abort the build; the message says exactly what to do):

- `check_overlay_base` — the OPC overlay's *base* must match the current
  upstream file. Used for the one remaining whole-file case if any survives;
  primarily a backstop.
- `check_config_version` — the literal stamped by both hermes entrypoints must
  equal `hermes_cli/config_defaults.py`'s `_config_version`. On mismatch, print
  the intervening `_migrate_to_N` names and refuse to build.

**`MemoryCore/Dockerfile`** stops COPYing a whole-file replacement. The overlay
becomes `patches/tencentdb-agent-memory/MemoryCore/patches/v3-meta-schemas.patch`,
applied in the deps-builder stage with `patch -p1 --fuzz=0`. `patch` is added to
that stage's apt list (it currently installs `python3 make g++`). Upstream
touching the hunk context stops the build with `Hunk #N FAILED`; upstream
additions elsewhere in the file flow through untouched.

Chosen over an anchored insertion script because `patch` is standard, the diff
is reviewable in-tree, and its failure message needs no explanation. The cost —
regenerating the patch when upstream edits lines adjacent to ours — is accepted:
in this repo an upgrade that touches the metadata schema file *should* be looked
at by a human.

### 2.3 `scripts/upgrade.sh`

- `--force-recreate` for **every** component, not just hermes. Without it the
  bootstrap one-shots do not re-run, which is the whole point of listing them.
- `SERVICES[paperclip]` gains `paperclip-bootstrap`.
- A new `BOOTSTRAP_SERVICES` mapping is not introduced: the one-shots are simply
  part of `SERVICES`, and `--force-recreate` makes them re-run. One table, not
  two.
- After `up`, the script **runs** `tests/migrations.sh <proj>` and exits
  non-zero if it fails, instead of printing a reminder.
- Component-specific post-steps that cannot be inferred (e.g. flushing orphaned
  proxy bindings when the key format changed) are surfaced by preflight and
  executed by the operator through the skill, not silently by the engine.

### 2.4 `tests/migrations.sh` (new — the seventh gate)

Live gate, one component per argument (`all` for every running one). Asserts
the thing `connectivity.sh` cannot see:

| Component | Assertion |
|---|---|
| buzz | `_sqlx_migrations` row count == `migrations/*.sql` at the pin, and `bool_and(success)`; log contains `Database migrations complete` |
| paperclip | `drizzle.__drizzle_migrations` count == `packages/db/src/migrations/*.sql` at the pin; log has no `Refusing to start against a stale schema` |
| hermes | every profile `config.yaml` has `_config_version` == upstream default; `grep -c '^platforms:'` == 1 per profile (the reconcile-duplicates-a-block failure); `agent.disabled_toolsets` still contains `kanban`; frontdoor `system_prompt` non-empty |
| tencentdb | core log has no `degraded` / `Store init failed`; `l1_fts` carries the v5 marker columns (`content_original,task_id,user_id,agent_id,version`); metadata store initialised (one `/v3/meta/*` call succeeds); every route in the new tag's route map answers non-500 |

The tencentdb route sweep is what turns gap 1 from invisible into a red gate:
after the overlay change it should pass, and if a future overlay ever clobbers
the schema module again, this is the assertion that catches it.

### 2.5 Proxy config reconcile

`proxy-entrypoint.sh` regenerates `config.yaml` on every boot. It is a pure
function of the environment; there is no supported reason to hand-edit it. When
the regenerated content differs from what is on disk, the old file is preserved
as `config.yaml.bak-<UTC stamp>` before being replaced — mirroring what hermes's
own `docker_config_migrate.py` does, so a surprise is recoverable.

### 2.6 Documentation

- `SETUP.md` and `references/risk-checklist.md` stop restating pins in prose;
  they point at `scripts/outdated.sh`, which derives the answer. The stale
  `v2026.8.16 (= v0.20.2)` strings go away rather than being corrected, because
  correcting them recreates the same drift next month.
- `patches/buzz/Dockerfile`'s comment loses its version literal — `upgrade.sh`'s
  `sed` only rewrites the `git clone` line, so any version in a nearby comment
  is guaranteed to drift.
- `references/risk-checklist.md` §7 gains the three-way rollback asymmetry
  (finding 7) and the corrected tencentdb facts: no version stamp, `metadata.db`
  migrates **lazily** (first `/v3/meta/*` request, not boot), failure is a
  silent degraded no-op, and the proxy binding format change is **ahead** of us
  in `v2.0.1`, not behind us.
- `SKILL.md`'s workflow replaces its hand-run checklist step with
  `scripts/upgrade-preflight.sh`, and its verification step with
  `tests/connectivity.sh` + `tests/migrations.sh`.

## 3. Testing

Offline, fixture-based, in the established `tests/outdated.sh` /
`tests/upgrade-workflow.sh` style (fake `git`/`docker` on `PATH`, real scripts
run in a temp root — no network, no live stack):

- `tests/upgrade-workflow.sh` extended: asserts `--force-recreate` is passed for
  every component, that `paperclip-bootstrap` is in the paperclip service list,
  and that a failing `tests/migrations.sh` makes `upgrade.sh` exit non-zero.
- `tests/upgrade-preflight.sh` (new): drives the preflight script against
  fixture repos covering each exit code and each per-component probe —
  including a fixture where the overlay base has drifted and one where
  `_config_version` has moved.
- `prepare.sh`'s new guards get a fixture case each (drifted / aligned).
- The patch application is covered by the real build; additionally a fixture
  case asserts `patch -p1 --fuzz=0` fails when context moves.

`tests/migrations.sh` itself is a live gate and joins `tests/fresh-install.sh`'s
gate list.

## 4. Out of scope

- Actually performing any of the three pending upgrades (buzz `desktop-v0.5.18`,
  paperclip `v2026.824.0`, tencentdb `v2.0.1`). This branch makes the machinery
  correct; running it is a separate, gated decision.
- Automatic rollback. GATE B stays an offer, per the existing skill.
- Upstreaming the `team_id`/`agent_id` schema change to tencentdb. Worth doing —
  it would delete the overlay entirely — but it is not a prerequisite.
- Migration/upgrade scripts for this stack's *own* state. AGENTS.md is explicit:
  one machine, adjust by hand, no maintained upgrade path for our own data.
